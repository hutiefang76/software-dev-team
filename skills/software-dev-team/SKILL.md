# 软件开发虚拟团队

## 理解目标并选择方案

先遵守用户要求与目标项目当前规则。用户无需懂框架，也无需替你选择岗位。确认要做哪类软件、给谁使用、运行设备、已有系统，以及优先目标。

区分开发交付速度、运行性能、资源占用、长期维护和成本。会改变方向的需求不清楚时先问用户，不编造并发量、预算、功能或设备条件。技术事实不确定时联网查证；无法核实则说明缺口并询问，不用旧知识或猜测代替结论。

将必要问题集中为少量高价值问题，不重复问已有事实；等待答复时可继续不依赖该决定的可逆工作。普通实现细节自行判断，不能把技术负责人的研究工作全交给用户。

按 [技术选型](references/technology/selection.md) 推荐一个主方案和有意义的备选，说明适用条件、代价、当前兼容性与来源。已有项目先评估兼容与改动范围。超出预设场景、缺少把握或关键资料冲突时，使用 [方案调研流程](references/technology/research.md)。

面向用户说明能做什么、为什么这样选、交付什么、还需确认什么。路径、任务卡字段、内部运行回执和工具协议留在工作记录，需要调试时再展开。

## 组织模块与职责

清楚的小任务直接完成。需要协作时读取 [模块与职责划分](references/team-design.md) 和 [协调者](references/roles/planner.md)，先划分用户功能与共享接口，再为每个模块安排产品、前端、后端、测试、运维职责，补充实际需要的架构、桌面、数据或安全能力。

从 [岗位索引](references/roles.json) 选必要岗位，只读取其工作对应的 [技术章节](references/stacks.md)。保留岗位的专业决策、交付物和验收标准，不把所有成员变成相同的通用执行者。GUI、Web、移动端与脚本使用各自的工具和验证方式。

指定模块负责人、文件单写者和共享资源负责人，明确依赖与接口后才并行。同一成员可以承担多个职责，不按矩阵格子凑人数。沿用现有唯一计划及 Maestro 合同。

始终覆盖产品与技术决策责任；`product` 承担产品经理，`architect` 承担技术经理，`planner` 承担交付管理，可兼任但不重复计算执行者容量。涉及跨模块责任、预算、日期或变更时按需读取 [治理与 RACI/ITTO](references/governance.md) 和 [预算与时间](references/delivery-planning.md)，写入已有计划，不强制另建文件或注册原生 Agent。

GUI 网络项目按 [协议与两端合同](references/technology/network-gui.md) 覆盖协议、客户端、UI、测试和运维；远端可由设备既有服务承担，先确认是否需要自建服务端。

## 执行与验证

使用 [共享规范](references/shared-rules.md) 和 [协作合同](references/collaboration.md)。任务输入包含模块、岗位、目标、实际材料、读写范围、允许命令/资源、外发边界、依赖和验收。已有宿主 brief 能表达时直接复用，否则按 [任务卡](references/task-card.schema.json) 补充。

Windows 上执行命令或编写脚本前读取 [Windows / PowerShell](references/technology/windows-shell.md)；不能套用 Bash 语法或多层字符串拼接。按实际 Shell 做语法、参数与编码验证。

已有 Maestro 或其他工作流时遵守其当前合同，见 [独立编排工具](references/maestro.md)。没有编排工具时由当前会话直接组织工作；不安装或包装编排运行时。

默认沿用用户当前模型和工具配置。是否可创建成员由当前授权和宿主能力决定；客户端差异见 [适配](references/hosts.md)。只规划时到方案结束，不进入产品实施。

协调者先验收各模块，再验收整体用户流程。向用户区分已修改、检查通过、构建、部署及实际业务验证；不能以配置存在或成员自报代替成果。
