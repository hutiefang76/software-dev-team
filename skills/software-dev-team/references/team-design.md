# 先分模块，再分职责

团队按两个维度组织：**模块／用户功能**决定要交付哪一块，**产品、前端、后端、测试、运维职责**决定这块工作由谁完成。岗位目录提供能力，不代替工作拆分。

## 1. 确定模块与依赖

从用户任务、业务边界和现有实现识别本轮涉及的模块；目录是定位依据，不自动等于功能模块。一个清楚的小改仍可由当前成员直接完成。

每个需要协作的模块明确：

- 模块 ID、用户目标、包含与不包含的功能。
- 现有入口、数据/接口边界，以及对其他模块的依赖。
- 模块负责人、共享文件或运行资源负责人。
- 对外合同与用户可观察的完成条件。

沿用项目已有模块划分与唯一计划。一个跨模块目标也只维护同一份现有计划或 Run 合同，不要求另建“团队计划”文件。

## 2. 将职责映射到模块

逐模块检查五项职责：

| 职责 | 模块内要明确的事情 |
|---|---|
| 产品 | 场景、功能范围、可见状态与业务验收条件 |
| 前端 | 页面/交互、接口消费、错误与恢复状态 |
| 后端 | 业务规则、API、授权、数据与执行合同 |
| 测试 | 模块合同、失败边界、依赖集成与独立验收 |
| 运维 | 配置、制品、部署、观测和必要的恢复条件 |

每一项分配负责人，或写“不适用”及具体原因。职责不等于必须新开成员：协调者可以兼产品，工程成员可以顺序处理多个模块；独立验收的限制要说明。桌面、数据、自动化、安全和架构岗位按模块实际技术补充，不另立团队层级。

## 3. 再拆可执行任务

任务同时带 `module_id` 与 `role_id`；输入引用本模块合同、必要的共享接口及上游成果。允许文件和运行资源明确到单写者，不因“某模块负责人”获得其他模块的写入权限。

先处理有多个消费者的接口、共享数据模型和公共组件，安排唯一负责人。依赖解除后，不重叠文件的任务才并行。多个模块确实需要同一文件时，交给共享文件负责人集成或安排顺序，不让多个成员竞争写入。

## 4. 按模块验收，再做整体集成

检查每个模块的职责交付是否齐全，再验证跨模块用户流程和共享资源。不能用“前端已完成”“全部单元测试通过”直接代替功能目标已完成。

已有 Maestro Session/Run 时，将模块及职责关系写入现有 brief/任务输入和证据，仍使用官方生命周期；不把此矩阵变成第二套状态系统。

## 示例：资料管理与消息通知

以下为虚构演示，只说明组织方式，没有实际成员或执行回执。

| 模块与目标 | 产品 | 前端 | 后端 | 测试 | 运维 |
|---|---|---|---|---|---|
| `profile`：用户可保存显示名 | 协调者兼产品，定义成功/失败行为 | 工程成员甲，资料表单 | 工程成员乙，资料 API 与授权 | 验收成员丙，保存与错误边界 | 本轮无部署改动，使用现有环境；交付负责人复核 |
| `notifications`：用户可查看未读消息 | 同一产品负责人，定义已读语义 | 工程成员甲，通知列表；与资料页面任务顺序安排 | 工程成员丁，查询与标记已读 | 验收成员丙，隔离验证与跨模块流程 | 交付成员戊，配置和观测 |

共享用户标识及错误格式先由架构/接口负责人确认。两个后端任务只有在文件不重叠且共享合同明确后并行。上述 2 个模块、5 类职责并不要求启动 10 个成员。
