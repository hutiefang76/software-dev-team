# 常见软件架构与选择条件

从用户任务和已有系统选最简单且足够可靠的形态，架构必须能对应到真实进程、接口、数据和部署。

| 形态 | 组成与适用条件 | 重点检查 |
|---|---|---|
| 服务端页面单体 | Spring MVC/SSM 或 Boot + 页面模板 + 数据库；表单流程集中、部署简洁 | 会话、表单校验、CSRF、事务、模板输出 |
| 前后端分离的模块化单体 | Vue/React 静态页面 + 一个按功能分模块的 Java/API 服务 + 数据库 | API/错误/权限合同、跨域、版本兼容与统一事务边界 |
| SSR/静态生成网站 | Next.js/Nuxt 或对应框架，必要时接已有业务 API | SEO、缓存、服务端/浏览器代码边界、认证与部署成本 |
| 本地桌面应用 | UI + 应用核心 + 本地文件/SQLite；外部服务按实际需要接入 | 离线、IPC、资源生命周期、安装与升级、备份 |
| 手机 App + API | 本地 UI/设备能力 + API + 服务端业务与数据库 | 弱网、缓存、同步冲突、登录、后台限制、上架 |
| 长任务执行 | API 提交 + 持久任务记录 + 工作进程；任务确实超过请求生命周期 | 幂等、取消、重试、进度与终态、崩溃恢复 |
| 微服务 | 团队边界、独立发布、容量与隔离需求明确后拆服务 | 网络失败、追踪、契约版本、运维成本、数据所有权与一致性 |

## 模块与分层

按业务功能组织模块，再在必要处区分入口/控制器、应用服务、领域规则与持久化。SSM 的 Controller → Service → Mapper 是可选的清晰分层，不等于必须建立大量空接口和 DTO 转换层。

共享用户标识、错误格式、权限与数据模型先明确唯一负责人。事务放在业务操作边界，跨服务不假设本地事务可覆盖所有效果。复杂领域可评估领域建模/端口适配，但不机械引入 DDD 或六边形架构。

## 从单体升级复杂度

先证明模块内问题无法用现有部署单元解决。不要为“以后可能扩展”默认加入网关、注册中心、消息队列、分布式事务和 Kubernetes。需要加入时说明触发条件、维护者、失败/恢复语义及可验证收益。

## 方案交付

包含目标、现状、候选/权衡、推荐、界面/服务/存储/部署图、模块与接口、实际工具、实施顺序、风险和验证。回退/恢复按改动影响设计，不为只读分析编造生产回滚步骤。专业资料不足时进入 [调研](research.md)。
