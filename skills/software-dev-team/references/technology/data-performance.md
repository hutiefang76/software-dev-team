# 数据处理与性能方案

## 从实际瓶颈出发

先确认数据量、并发、延迟/吞吐、内存预算、设备与完成条件。检查 SQL/索引、网络往返、序列化、渲染、磁盘和算法，不能仅凭语言决定整体性能。

| 工作 | 候选与工具 | 验证重点 |
|---|---|---|
| 事务型业务数据 | 现有 MySQL/PostgreSQL，迁移沿用项目工具 | 索引、执行计划、事务、锁、连接池与真实查询 |
| 本地小型持久数据 | SQLite 等嵌入式存储 | 并发写、锁、备份与应用关闭；不假设多机共享安全 |
| Python 数据/模型流程 | 标准库/已有数据库，必要时 Polars/DuckDB 等 | schema、粒度、NULL/重复、内存、增量及幂等 |
| 长计算或模型服务 | FastAPI 请求层 + 独立工作进程/任务记录 | CPU 与 I/O 区别、超时/取消、恢复、资源上限 |
| 性能关键模块/CLI | Rust，必要时 Rayon/Tokio 等符合负载的库 | 所有权、分配、并发模型、目标平台和基准 |
| 网络服务 | Axum + Tokio 等现有成熟路线 | 超时、背压、有界队列、任务关闭；阻塞工作不直接占异步执行器 |

依赖只是候选。先判断现有栈是否足够，新增前查官方当前要求、兼容与许可，避免一个任务同时引入多种查询引擎。

## 性能工作交付

固定代表性数据、硬件/系统、实际版本、编译配置、预热与测量方式。按目标用 Criterion、cargo bench、JFR/profiler、k6 等合适工具；不把不同负载的结果放在一起宣称提升。

比较优化前后吞吐、延迟分位、内存/CPU、错误率及正确性；记录重复次数和变动。只有基准计划或小样本时明确限制。

## 数据正确性

确认来源、粒度、键、显式列、NULL、时区、增量边界与重跑语义。表/行数相同不是内容正确。先用合成或获准的隔离数据，生产 DDL/DML 与迁移不由普通分析授权推出。

依据：[Rust](https://rust-lang.org/)、[Axum](https://docs.rs/axum/latest/axum/)、[FastAPI](https://fastapi.tiangolo.com/)。
