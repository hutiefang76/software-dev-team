# 技术负责人寻找新方案

用于陌生技术、目录外工作、关键假设未证实、来源冲突或用户要求最新推荐的情况。

1. **定义问题。** 明确设备、输入输出、规模、交付/性能目标、网络与维护约束。业务事实缺失问用户；技术事实先查证，仍不确定时说明具体分歧，不编造答案。
2. **按能力检索。** 例如拆成“离线识别、目标系统、设备 SDK、部署方式”，用中英文从不同角度寻找候选，不只搜索一个心仪框架。
3. **核对原文。** 先查官方文档、SDK、版本发布、支持周期、兼容矩阵、安全公告和维护中的官方示例。打开页面，确认日期、稳定/预览状态及平台限制。社区文章与排行榜只作线索。
4. **比较候选。** 比较能力覆盖、平台、开发成本、性能/资源、维护、许可、依赖、运维与迁移。权重来自用户目标；没有数据不编造数字评分。标明官方事实、工程判断、项目验证和待核实。
5. **消除关键风险。** 获准实验后在隔离目录做最小 PoC，验证会改变决策的一条链。固定真实版本、输入、设备和测量方法；不能运行就交付验证计划，不写成通过。
6. **形成推荐。** 给一个主方案、必要备选、选择及放弃原因、来源/核验日期、风险、实施与验证方式。需要用户决定的是实际权衡，如离线还是托管，而不是让用户替负责人研究 API。
7. **落到执行。** 关键条件明确后映射到功能模块、岗位、接口、具体工具和验收。复用现有唯一计划，不另建第二套进度系统。

示例：用户说“大量节点，交互要流畅”。先确认节点/边规模、设备和操作，再调查 Canvas/WebGL、布局、增量更新及可视区裁剪；网络与 SQL 也可能是瓶颈。使用相同数据做授权验证，不能仅因“高性能”就决定全系统改用 Rust。
