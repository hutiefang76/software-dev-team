# 分工与任务合同

协调者持有整体目标与集成责任。先按 [模块与职责](team-design.md) 划分功能和依赖，再为模块映射专业职责。确认任务是否真正能并行后才派发；一个小改不要求运行完整团队。

## 最小合同

每个成员需要以下事实，可用宿主现有 brief、简短文字或 [JSON Schema](task-card.schema.json)，不要为同一目标维护多份合同：

| 字段 | 内容 |
|---|---|
| 目标与交付 | 一个可复核的工作单元及结果位置 |
| 模块与职责 | `module_id` 对应功能模块，`role_id` 对应承担的职责 |
| 输入与依赖 | 能实际读取的材料、基线及上游成果 |
| 范围 | 具体可读/可写文件、允许命令与运行资源 |
| 负责人 | 文件单写者、共享资源负责人和协调者 |
| 调用与外发 | 工具、实际模型；外发目的地及允许内容 |
| 验收与停止 | 观察什么才算完成；超范围或接口冲突如何返回 |
| 责任与阶段（按需） | RACI 的唯一 A、实际 R/C/I；ITTO 的输入、方法、输出及出口条件 |
| 时间与费用（按需） | 真实执行者和共用容量、估算/实际/剩余、币种、上限、截止与修正次数 |

权限与验收来自当前有效要求。无权限运行不等于允许把操作交给另一个成员。

任务卡可选 `raci`、`itto`、`delivery` 对应 [治理](governance.md) 和 [计划](delivery-planning.md)。只有当前任务需要才补齐；不改变旧任务卡兼容性。空缺用 null 表示未知，结构合法不等于已批准预算或已执行。参考 [带交付约束的示例](delivery-task-example.json)。

## 推荐流程

协调者先确认各模块边界、共享接口和模块负责人，再分配独立任务。实现与验证可顺序进行；独立测试上下文从需求和产物读取事实，不以实现者结论代替检查。高耦合文件由单写者集成。按模块验收后，再验证跨模块用户流程。

已有 Maestro Run 时沿用同一 Session 的合同、上游产物和当前版本。角色不能重建第二套完成协议或自行推进未授权阶段。

没有子 Agent 工具时由当前成员顺序使用必要岗位。将结论写成自查结果，不声称多个独立成员参与。

## 回传

返回任务与角色、实际工具/模型/成员 ID、差异或成果位置、命令与实际结果、未完成及下一步。协调者复核验收条件后决定整体状态。

[只读示例任务卡](dispatch-example.json) 是演示材料，不提供真实执行或外发授权。
